# テーブル定義書

## users

### 概要

CircuitStockを利用するユーザーを管理する。

| カラム名 | 論理名 | データ型 | PK | FK | NULL | UNIQUE | DEFAULT | 制約・補足 |
|---|---|---|---|---|---|---|---|---|
| id | ユーザーID | BIGINT | ○ | - | 不可 | - | - | 自動採番 |
| user_name | ユーザー名 | VARCHAR(32) | - | - | 不可 | - | - | 最大32文字、空文字不可、スペースのみ不可 |
| email | メールアドレス | VARCHAR(255) | - | - | 不可 | ○ | - | 最大255文字、メールアドレス形式、大文字・小文字を区別しない  |
| password | パスワード | VARCHAR(255) | - | - | 不可 | - | - | ハッシュ化して保存、入力時15〜64文字 |



## categories

### 概要

部品を分類するためのカテゴリを管理する。

| カラム名 | 論理名 | データ型 | PK | FK | NULL | UNIQUE | DEFAULT | 制約・補足 |
|---|---|---|---|---|---|---|---|---|
| id | カテゴリID | BIGINT | ○ | - | 不可 | - | - | 自動採番 |
| user_id | ユーザーID | BIGINT | - | ○ | 不可 | ※ | - | users.idを参照、ON DELETE CASCADE （ユーザー削除時に連動削除） |
| category_name | カテゴリ名| VARCHAR(32) | - | - | 不可 | ※ | - | 最大32文字、空文字・スペース・改行・タブ不可、大文字小文字、全角半角は同一扱い |

### 制約・補足

- 同一ユーザー内では、同じカテゴリ名を登録不可とする。
- 別ユーザーであれば、同じカテゴリ名を登録可能とする。
- カテゴリ名の登録・変更時は、同じ入力ルールと重複チェックを適用する。
- カテゴリ名は、大文字小文字・全角半角を正規化して保存する。
- カテゴリ名には記号を使用可能とする。
- カテゴリ名が32文字を超える場合は、切り捨てず登録エラーとする。
- 使用中のカテゴリは削除不可とする。
- 使用中のカテゴリを削除する場合は、そのカテゴリを参照している部品を別カテゴリへ変更し、参照0件にしてから削除する。
- 部品はカテゴリ名ではなくカテゴリIDを参照するため、カテゴリ名変更時に部品データ自体の更新は不要とする。
- `user_id`はユーザーが入力せず、ログイン中ユーザーのIDをシステム側で設定する。
- `user_id`は画面上では基本的に表示しない。

### UNIQUE制約

※ `user_id`単体、`category_name`単体にはUNIQUE制約を付けない。

複合UNIQUE制約として、以下の組み合わせで重複を禁止する。

`user_id + category_name`

ただし、カテゴリ名は大文字・小文字、全角・半角を同一扱いとする。

### 実装時の検討事項

Issue #5では、以下を**仕様として確定**する。

- 同一ユーザー内ではカテゴリ名の重複を禁止する。
- 大文字・小文字は同一として扱う。
- 全角・半角は同一として扱う。
- カテゴリ名を正規化して保存する。
- DB側でも重複を保証する。
- 空文字・スペース・改行・タブなどの禁止について、Laravel側のバリデーションに加えてDB側でも制約を設ける。

一方、PostgreSQLで大文字小文字・全角半角を同一扱いにした上で複合UNIQUE制約を実現する具体的な方法は、実装時に決定する。

候補としては、正規化後の値を用いたUNIQUE制約や、`LOWER()`等を利用したインデックス、PostgreSQLの機能・拡張などを検討する。

Laravelでは、`user_id`の外部キー定義に`foreignId()`と`constrained()`を使用し、ユーザー削除時の連動削除を設定する想定とする。

## parts

### 概要

CircuitStockで利用する部品を管理する。

| カラム名 | 論理名 | データ型 | PK | FK | NULL | UNIQUE | DEFAULT | 制約・補足 |
|---|---|---|---|---|---|---|---|---|
| id | 部品ID | BIGINT | ○ | - | 不可 | - | - | 自動採番 |
| user_id | ユーザーID | BIGINT | - | ○ | 不可 | ※ | - | users.idを参照、ON DELETE CASCADE（ユーザー削除時に連動削除） |
| category_id | カテゴリID | BIGINT | - | ○ | 不可 | - | - | categories.idを参照、参照中のカテゴリは削除不可 |
| storage_id | 保管場所ID | BIGINT | - | ○ | 不可 | - | - | storages.idを参照、参照中の保管場所は削除不可 |
| part_name | 製品名 | VARCHAR(32) | - | - | 不可 | ※ | - | 最大32文字、空文字・前後スペース・制御文字不可、途中スペース・記号可 |
| model_number | 型番 | VARCHAR(64) | - | - | 不可 | ※ | - | 最大64文字、空文字・前後スペース・制御文字不可、途中スペース・記号可 |
| stock_quantity | 在庫数 | INTEGER | - | - | 不可 | - | 0 | 0以上1000以下、CHECK制約、ユーザーによる直接編集不可 |
| created_at | 登録日時 | TIMESTAMPTZ | - | - | 不可 | - | - | 新規登録時にシステムが自動設定 |
| updated_at | 更新日時 | TIMESTAMPTZ | - | - | 不可 | - | - | 新規登録・更新時にシステムが自動設定・更新 |

### 制約・補足

- 部品登録・更新時に指定できるカテゴリ・保管場所は、ログイン中ユーザーが所有するものに限定する。
- 製品名と型番は、大文字・小文字、全角・半角を同一扱いとする。
- 製品名と型番の全角・半角は正規化して保存する。
- 製品名と型番の英字の大文字・小文字は入力時の表記を維持して保存し、重複判定時のみ区別しない。
- 製品名と型番の具体的な正規化・重複判定方法は実装時に決定する。
- 部品新規登録時の在庫数は必ず0とする。
- 登録時点で実在庫が1個以上ある場合は、部品登録後に別途「入庫」として登録し、在庫数を増加させる。
- 在庫数はユーザーが直接編集できないものとし、入出庫登録によってのみ増減させる。
- 在庫数の変更と入出庫履歴の登録は同時に行う。
- 在庫数は0以上1000以下とし、1000を超える在庫数は登録不可とする。
- 在庫数が0になった場合も部品データは削除せず、通常の部品として保持する。
- MVPでは同一部品を複数の保管場所に分けて管理しない。
- メーカー情報はMVPでは管理せず、将来の拡張時に追加を検討する。
- created_at、updated_atはユーザーが入力・変更しない。
- created_atは登録後に変更しない。
- updated_atは製品名、型番、カテゴリ、保管場所、在庫数など、部品レコードが更新された場合に自動更新する。

### UNIQUE制約

※ user_id単体、part_name単体、model_number単体にはUNIQUE制約を付けない。

同一ユーザー内では、製品名と型番の組み合わせが同一の部品を重複登録不可とする。

重複判定は、以下の組み合わせを基準とする。

`user_id + part_name + model_number`

ただし、part_nameとmodel_numberは、大文字・小文字、全角・半角を同一扱いとして判定する。

具体的なDB側のUNIQUE制約・インデックス・正規化方法は実装時に決定する。

### 実装時の検討事項

Issue #5では、以下を**仕様として確定**する。

- 部品は必ずユーザー、カテゴリ、保管場所に紐づく。
- 部品登録・更新時に選択できるカテゴリ・保管場所は、ログイン中ユーザーが所有するものに限定する。
- 同一ユーザー内では、製品名と型番の組み合わせが同一の部品を重複登録不可とする。
- 製品名と型番の大文字・小文字は同一として扱う。
- 製品名と型番の全角・半角は同一として扱う。
- 製品名と型番の全角・半角は正規化して保存する。
- 製品名と型番の大文字・小文字は保存時の表記を維持する。
- DB側でも部品の重複を防止する。
- 在庫数は0以上1000以下とする。
- 在庫数は部品編集画面から直接変更できない。
- 在庫数の変更は入出庫登録によってのみ行う。
- 在庫数の変更と入出庫履歴の登録は整合性を保って同時に行う。
- カテゴリまたは保管場所が部品から参照されている場合、そのカテゴリ・保管場所は削除不可とする。

一方、以下の具体的な実装方法は実装時に決定する。

- PostgreSQLで大文字・小文字、全角・半角を同一扱いにした複合UNIQUE制約を実現する方法
- 製品名・型番の正規化方法
- 空文字、前後スペース、制御文字などの禁止をLaravel側・DB側でどのように保証するか
- 在庫数の0以上1000以下を保証するCHECK制約の具体的な記述方法
- 在庫数更新と入出庫履歴登録を同一トランザクションで処理する具体的な方法
- created_at、updated_atにLaravelのtimestampsTz()等を使用するか
- category_id、storage_idの外部キー削除動作にRESTRICTまたはNO ACTIONのどちらを使用するか

Laravelでは、user_id、category_id、storage_idの外部キー定義にforeignId()、constrained()等を使用する想定とする。

user_idはユーザー削除時に部品も連動削除する。

一方、category_id、storage_idについては、部品から参照されているカテゴリ・保管場所をDB側でも削除不可とし、RESTRICTまたはNO ACTIONなどを候補として実装時に決定する。



## stock_movements

### 概要

CircuitStockで利用する部品の入庫・出庫の履歴を管理する。

| カラム名 | 論理名 | データ型 | PK | FK | NULL | UNIQUE | DEFAULT | 制約・補足 |
|---|---|---|---|---|---|---|---|---|
| id | 入出庫ID | BIGINT | ○ | - | 不可 | - | - | 自動採番 |
| part_id | 部品ID | BIGINT | - | ○ | 不可 | - | - | `parts.id` を参照、参照中の部品は物理削除不可 |
| movement_type | 入出庫区分 | VARCHAR(16) | - | - | 不可 | - | - | `in` / `out` のみ許可、画面では「入庫」「出庫」と表示 |
| quantity | 数量 | INTEGER | - | - | 不可 | - | - | 1以上の整数 |
| reason | 理由 | VARCHAR(32) | - | - | 可 | - | - | 最大32文字、未入力時は `NULL` |
| created_at | 登録日時 | 日時型 | - | - | 不可 | - | - | 新規登録時にシステムが自動設定 |

### 制約・補足

- 入出庫履歴は登録後に変更・削除しない。
- 入力ミスは、新しい入出庫履歴を追加して訂正する。
- `updated_at` は持たず、`created_at` のみ使用する。
- 登録日時は日本時間で扱い、時・分・秒まで保存する。
- 画面では登録日時を「年月日＋時・分」まで表示する。
- `stock_movements` には `user_id` を持たせず、`part_id → parts.user_id` を通して所有ユーザーを判定する。
- 入出庫登録時は、ログイン中ユーザー自身が所有する部品のみ指定可能とする。
- ユーザーは製品名などから部品を選択し、システムが対応する `part_id` を設定する。
- 登録後に `part_id` を別の部品へ変更しない。
- 入出庫履歴から参照されている部品は物理削除不可とする。
- 入出庫履歴から参照されている部品を削除する場合は論理削除とし、`parts.id` と `part_id` の参照関係を維持する。
- 論理削除済み部品は新しい入出庫履歴の登録対象として選択不可とする。
- 論理削除された部品の過去の入出庫履歴は表示し、対象部品が「削除済み」であることが分かるようにする。
- `movement_type` はDBでは `in` / `out` を保存し、それ以外の値は許可しない。
- MVPでは入出庫区分を「入庫」「出庫」の2種類とする。
- 棚卸調整や廃棄などは、入庫または出庫として登録し、具体的な内容を `reason` に記録する。
- 入出庫区分を誤って登録した場合は、反対区分の履歴を新たに追加して訂正する。
- `quantity` は1以上の整数とし、0・負数・小数・文字は許可しない。
- DB側でも `quantity >= 1` を保証する。
- 入庫後の `parts.stock_quantity` が1000を超える場合は登録不可とする。
- 出庫後の `parts.stock_quantity` が0未満になる場合は登録不可とする。
- 入出庫履歴の追加と在庫数の更新は、必ずセットで成功または失敗させる。
- `reason` は任意入力とし、未入力時は `NULL` とする。
- `reason` は空文字・スペースのみ・改行・タブなどの制御文字を許可しない。
- `reason` の前後にある半角・全角スペースは保存前に削除する。
- `reason` の途中のスペースは許可する。
- `reason` が32文字を超える場合は、切り捨てず登録エラーとする。
- `part_id` と `created_at` にインデックスを設定する。
- 単純な値のルールはDB側にも制約を設定し、複数テーブルや現在の在庫状態にまたがる業務ルールはアプリ側で制御する。

### UNIQUE制約

- `id` は主キーのため一意とする。
- `id` 以外にはUNIQUE制約を設定しない。
- 同じ部品・登録日時・入出庫区分・数量などを持つ履歴が複数存在することは許可する。
- 二重送信への対策はUNIQUE制約では行わず、アプリ側の仕組みとして検討する。

### 実装時の検討事項

- Laravelで `created_at` のみを使用する場合のモデル・マイグレーション設定を確認する。
- PostgreSQLで `created_at` に使用する具体的な日時型は、Laravelのマイグレーション仕様に合わせて決定する。
- `movement_type` に `in` / `out` 以外を保存できないよう、DB側の制約方法を決定する。
- `quantity >= 1` のDB制約方法を決定する。
- 入出庫履歴追加と `parts.stock_quantity` 更新を一体として処理する方法を実装時に決定する。
- 二重送信を防ぐ具体的な方法は実装時に検討する。
- 入出庫履歴の検索・絞り込み条件は画面設計時に詳細を決定する。
- MVPでは `part_id` と `created_at` にインデックスを設定し、今後検索条件を拡張する場合は追加インデックスの必要性を検討する。
